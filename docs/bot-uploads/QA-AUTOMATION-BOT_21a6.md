6. **Be gentle with www.sportstech.de.** One page load at a time, ≥ 1.5 s between loads, no parallel browsers. Cloudflare rate-limits at roughly 50 fast loads (HTTP 429 or a challenge page). If that happens, stop, record the gap as OPEN, and do not retry in the same run.

8. **Secrets:** never print, log, commit or paste tokens. Read them from the macOS Keychain (below).
9. **Personal files stay private:** never attach or post the hand-off files (`handoff/`, HANDOFF.md, the zip, MCP setup, memory copies, this runbook) or CVR / incident reports (`runs/cvr-*`) to Wrike. On a task, attach only that task's `qa-bot-validation-<id>-roundN.pdf`.

## 6. Validation procedure (per task)

1. **Fetch** the task. Read the goal, scope and **acceptance criteria** in the description, the decisions in the comments (e.g. "keep PDP countdown as is"), and DevBot's latest "changed / checked / open / expected" list. Open every attached image (design references, bug screenshots). Figma links need a login; if you can't open them, say so and compare against the attached images.
2. **Pages:** use the URLs DevBot or the task names (e.g. `/products/sxm150-smith-machine`). Otherwise pick where the component appears: `/` for header or announcement items, a PDP (`/products/f75-profi-laufband`, `/products/f37s-profi-laufband`, `/products/stread-fold-pro-laufband`) for product items, `/cart` for cart items, the named collections.
3. **Preview URL:** `https://www.sportstech.de/<locale-prefix><path>?preview_theme_id=<id>&pb=0` (`pb=0` hides Shopify's preview bar). Confirm on every load that `window.Shopify.theme.id` equals the preview id; if not, the result is invalid.
4. **Device matrix (minimum):**

   | Config | Engine | Viewport | Notes |
   |---|---|---|---|
   | MOB-Safari | Playwright WebKit | 375×812, dpr 2, touch, iPhone UA | stands in for iOS Safari (not a real device) |
   | MOB-Chrome | Chromium | 375×812, dpr 2, touch, Android UA | |
   | DSK-Chrome | Chromium | 1440×900 | |
   | DSK-Safari | WebKit | 1440×900 | |

   Run all 7 locales on preview; run live `de` on each config as the "before" baseline, plus live in the other locales when comparing copy.
5. **Checks:** cover every acceptance criterion and every DevBot claim you can automate:
   - element present, and styles vs design (colours, radius, font sizes, spacing)
   - copy per locale: translated, not hardcoded; compare with live
   - no wrapping or overflow at 375 and 1440 (`scrollWidth > clientWidth`, element right edge > viewport, text line count via `Range.getClientRects`)
   - behaviour: clicks, links localized, timers tick, variant change → price/URL, add-to-cart → `/cart/add` 200 → `/cart.js` count → cart → checkout page load, then clear the cart
   - `prefers-reduced-motion` turns animations off
   - CLS (PerformanceObserver `layout-shift`), new JS errors vs live (ignore ones live also has, e.g. Safari `button?.unload`)
   - unrelated areas unchanged: compare live vs preview markup and computed styles
   - WCAG contrast: 4.5:1 for normal text
   - **New round of an already-reviewed task:** re-check every earlier QA finding, not only what DevBot says it changed. Archive the previous round's files in `runs/<id>/roundN/`.
   - **Links in comments without `preview_theme_id`** (e.g. `…/de-ch/products/stread-pro-laufband?pb=0`) open the live site. Test that page on the preview theme and say so in the comment.
   - **Cookie banner** (Pandectes, in a shadow DOM, so plain JS selectors don't reach it): decline with a Playwright role locator such as `getByRole('button', { name: /^(ablehnen|rechazar|refuser|tout refuser|rifiuta|weigeren|afwijzen)/i })`. If a banner or popup is still open, taps are intercepted and screenshots show the banner. Check.
   - **Desktop sticky add-to-cart bar** only shows when the main add-to-cart button is out of view. The product column is sticky, so with the add-on list open it never shows. For desktop cart checks use the main button `button.product-form__submit:visible` (the first `form[action*="/cart/add"]` can be a hidden form).
   - **Screenshots can be misleading**: dimmed overlays, a cookie banner or the Klaviyo popup can cover the element. Look at every screenshot you put in a report and drop or retake wrong ones.
   - **VISUAL LAYOUT REGRESSION (mandatory since 28 Sep, after Jonas spotted what QA missed on the MOOV cards 4557802032):** whenever the change touches product cards, grids, carousels, PDP/collection layout, fonts/padding or text content, run `node lib/card-layout.mjs '<runs json>' <out.json> <evidenceDir>` on the preview AND live at 360, 375, 430, 768 and 1440 px, DE plus at least FR/NL/IT (long words), on every collection/page that shows the component. It reports: text covered by another element (incl. chat bubble), text past the card edge or clipped, words split mid-word, and uneven cards in a row (height / price / button offset > 4 px). Grading: covered, past-edge or clipped text = DEFECT (customer-visible); in the changed component it blocks. Uneven price/button rows caused by the change = DEFECT when the design shows aligned cards, otherwise WARN; compare with live (existing unevenness = also on live). Always open the evidence crops and look at them: long German compounds (Selbstschmierfunktion, Bodenschutzmatte, Gelenkschonend) at 360-375 px are the typical failure.
5b. **Source of truth: Shopify Admin API (read-only, since 26 Sep 2026)** via `python3 lib/shopify.py` (credentials in the Keychain, token renewed automatically). Use it in EVERY validation, and put the results in the report:
   - `theme-diff <previewThemeId> --out runs/<id>/theme-diff`: the exact files the preview changes vs the live theme. Check that the change is limited to what the task / DevBot claims. Unexpected files (e.g. footer, other sections) are findings. A file that differs only because live moved on (preview **behind live**, e.g. an already released section reverted) is a DEFECT risk: merging a stale branch can undo a release. Changed `locales/*.json` keys must exist in all 6 language files with real translations (not German copies).
   - `product <handle>`: variant prices and compare-at prices **per market** (DE AT CH ES FR IT NL, via contextual pricing), availability, inventory. Compare with what the storefront shows (PDP, sticky bar, total block, cart). A mismatch is a DEFECT. Also flag odd prices (e.g. unrounded auto-converted CHF amounts), available variants with negative stock, and compare-at ≤ price.
   - `translations <handle>`: product title / description / SEO translations missing or outdated in ES/FR/IT/NL (DE is the source). Missing or outdated = DEFECT (wrong-language text for customers).
   - `markets`, `themes`, `gql '<read-only query>'` for anything else (metafields, metaobjects, discounts).
   - Privacy: never query orders, customers or checkouts (the helper refuses). The app has one write scope (`write_marketing_integrated_campaigns`); the helper refuses all mutations.
   - In spec.json add the Admin API results to passed / defects / warn with the exact values (e.g. "Admin API CH price 309.00 CHF = PDP CHF 309.00 ✅") and list the theme-diff files in `tested`/`open` so DevBot sees the precise scope.
6. **Screenshots:** cropped element before (live) and after (preview) per device and locale, plus a first-viewport shot per device. Naming: `YYYYMMDD-HHMM-<CFG>-<live|preview>-<locale>-<what>.png` (Europe/Berlin time).
7. **Classify** each item:
   - **PASS**: works as required.
   - **FAIL** ❌: an acceptance criterion is not met.
   - **DEFECT** 🐞: something a customer can see is wrong, **even if it already exists on live**. Examples: wrong price, currency or amount (e.g. "€CHF 1,337.00"); text in the wrong language; broken, missing or wrong link or CTA; a tap blocked by an overlay; layout that breaks or hides content; a wrong total in cart or checkout. Never grade these as minor just because live has them too. Say "also on live" and name the pages or markets affected.
   - **WARN** ⚠️: purely cosmetic or minor (design detail, spacing, contrast below WCAG AA, layout at its limit, a DevBot claim that is slightly off).
   - **OPEN**: cannot be automated (real iOS device, theme-editor click test, Figma behind login, rate-limited).
   - Always look at the screenshots themselves as well as the numbers. A double currency symbol, clipped text or an overlay is a finding, even if the automated check "passed".
8. **Verdict:**
   - `NOT READY` if there is any FAIL, or any DEFECT in the component or area the PR changes. The fix is cheapest in the same PR: recommend fixing it there, or getting an explicit owner decision to ship without it.
   - A DEFECT outside the changed area does not block. Report it and create the defect task automatically with `wrike.py defect` (no duplicates; Jonas assigned; Ali, santhana, Thomas tagged), then link it in the QA comment.
   - Otherwise `READY`. Wording: `NOT READY – N acceptance criterion failed, D defect(s), M minor`.

> **AUTOMATIC DEFECT TASKS (Soumya, 28 Sep 2026):** for every DEFECT that is NOT caused by the change under test (pre-existing on live, outside the PR, app/content issues), create a Wrike defect task yourself – no approval needed – with `python3 lib/wrike.py defect --key <stable-slug> --keywords "<a|b,c>" --title "DEV: <what is wrong> (<markets>)" --desc <desc.html> --source <taskId> --files <crops…>`. ## 6d. Store-data tasks by the Shopify Bot (since 28 Sep 2026)

The Shopify Bot (formerly DEV BOT Shopify, same Wrike user `KUAZALYY`) also changes store data: metafields and metaobjects, product FAQs and Knowledge Base entries for AI agents, gallery order and image alt texts, discount codes, new product listings (always DRAFT), product and collection fields, redirects and menus. Tasks may carry `[data]` or `[code]`. **Store data has no preview: it is live the moment it is saved.** The bot posts a frozen plan (old → new) and writes only after "@Shopify Bot push to live" (sensitive changes – prices, product status, discounts, redirects, menus, collections, new products – and plans > 25 items need "push to live confirm" / "confirm N"). "@Shopify Bot rollback" restores the snapshot; discounts are deactivated, never deleted. Always blocked for the bot: deleting, inventory, translations (T Lab), orders/customers/payments, themes outside the code flow, apps, shop settings.

QA for data tasks:
1. **Plan review (when a person asks "@QA Automation Bot validate" on a plan, before the push):** read-only.
